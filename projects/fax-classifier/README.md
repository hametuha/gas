# fax-classifier — FAX を Gemini で仕分け、受注は明細まで抽出

Drive の「FAX」フォルダに Zapier が保存したPDFを、Gemini で読んで処理する GAS。
2段構えになっている。

```
[Zapier] FAX添付メール → Drive「FAX」フォルダに保存 + Gmail に "FAX" ラベル
                                │
                                ▼
[ステージ1: 分類]  processFaxFolder()
  1. FAXフォルダ直下のPDFを列挙（子フォルダ内=処理済みは対象外）
  2. 各PDFを Gemini で分類 → {category, confidence, reason}
  3. 確信度 >= 0.75 のものだけ該当フォルダへ移動。低いものは「不明」へ
  4. 全件を「FAX仕分けログ」シートに記録
                                │
                                ▼ 受注フォルダに入ったPDF
[ステージ2: 受注明細の抽出]  extractOrders()
  1. 受注フォルダ直下のPDFを列挙（「抽出済み」子フォルダは対象外）
  2. 自社刊行物リストを候補として与え、Gemini で注文内容を抽出
  3. ISBN・書名・冊数・発送先を機械検算し、怪しい行に「要確認」を立てる
  4. 1行1明細で「受注明細」シートへ記録し、PDFを「抽出済み」へ移動

  ↑ この2つを runPipeline() が続けて実行（1時間毎トリガー）

[毎日18時トリガー]  dailyReport()
  当日分の分類内訳と受注抽出の結果を1通のメールにまとめて送る。
  要確認があれば理由とリンクを添える。動きがない日は送らない。
```

フォルダID（親=受信箱・子=受注/返品/営業/不明）は Config.js に直書き。
フォルダID・scriptId は秘密ではない（それ自体ではアクセス不可。Drive/Apps
Script の権限が別途必要）。自分の環境に合わせて Config.js を書き換えて使う。

## 設計上の安全策

### 共通

- **DRY_RUN**: 初期は判定・抽出してログに残すだけで**ファイルを移動しない**。
  精度を確認してから `false` にする。ステージ1と2で別フラグ。
- **監査ログ**: DRY_RUN でも本番でも全件を記録。判定理由も残すので後から検証できる。
- **日次サマリー**: 毎日18時に当日分をまとめてメール。0件の日は送らない。

### ステージ1（分類）

- **確信度で足切り**: `CONFIDENCE_THRESHOLD`(0.75) 未満は order/return/sales でも「不明」に落とす。
  注文を返品と取り違える誤仕分けを避けるため、迷ったら不明に寄せる。

### ステージ2（受注明細の抽出）

**このシートは「発注データ」ではなく「人間が検算する下書き」**として設計している。
理由は、抽出項目によって機械検算できる／できないが大きく違うため。

| 項目 | 検算手段 | 危険度 |
| --- | --- | --- |
| ISBN | チェックディジット + 書籍マスタ照合 | 低 |
| 書名 | 書籍マスタ照合（bigram類似度） | 低 |
| 取次・書店 | 両方とも空なら発送先不明として弾く | 中 |
| **冊数** | **なし** | **最高** |

手書きの「1」と「7」、「3」と「5」の誤読を見破る術はない。
よって以下を徹底している。

- **推測させない**: プロンプトで「読み取れない項目は必ず null。推測・創作は厳禁」を強制。
  空欄は人が補えるが、もっともらしい嘘は補えない。
- **要確認フラグ**: ISBN不正／マスタ不在／書名不一致／冊数の欠落・異常値／
  確信度不足／発送先不明 のいずれかで立つ。理由も併記する。
- **書名を2列並べる**: 「書名(FAX)」と「書名(マスタ)」を隣に置き、目視検算を1秒で済ませる。
- **「対応済み」ではなく「抽出済み」**: GASの抽出完了と業務完了（発送済み）は別物。
  同じフォルダで表すと出荷漏れを招くので、業務完了は受注明細シートの
  **ステータス列**で人間が管理する。GASはこの列に触らない。

### 書籍マスタ

破滅派のISBNは `978-4-905197-XX-C`。出版社記号が6桁なので書籍記号は2桁、
つまり刊行物は**最大100点**しか存在しえない。全パターンを列挙して
[openBD](https://openbd.jp/) に一括照会すれば、完全なマスタが1リクエストで手に入る。

openBD は JPRO 登録ベースなので電子書籍などは載らない。マスタシートに手で足せば
よく、`refreshBookMaster()` は出典が「手動」の行を上書きも削除もしない。

## セットアップ

### 1. Apps Script プロジェクトを用意

```bash
cd projects/fax-classifier
npx clasp create --type standalone --title "FAX Classifier" --rootDir src
npx clasp push
```

### 2. Gemini APIキーを取得

[Google AI Studio](https://aistudio.google.com/apikey) でAPIキーを発行する。
**顧客の注文情報を扱うため、課金を有効にした（有料枠の）キーを使うこと**
（有料枠は入力がモデル学習に使われない）。

### 3. スクリプトプロパティを設定

Apps Script エディタ → プロジェクトの設定 → スクリプトプロパティ で以下を登録：

| プロパティ名 | 値 |
| --- | --- |
| `GEMINI_API_KEY` | AI Studio で発行したキー（**秘匿。コードには書かない**） |
| `NOTIFY_EMAIL` | （任意）日次サマリーの宛先。未設定なら実行ユーザー宛 |

`LOG_SHEET_ID` は `setup()` が自動作成する。フォルダIDは `Config.js` に直書き。

### 4. 抽出済みフォルダを作る

受注フォルダの中に「抽出済み」フォルダを作り、そのIDを
`Config.js` の `ORDER.EXTRACTED_FOLDER_ID` に設定する。
未設定のまま本番運転しようとすると `extractOrders()` は例外で止まる
（移動できないと同じPDFを無限に再処理して課金が無駄になるため）。

### 5. 初期化 & 権限承認

エディタで `setup()` を実行。初回は Drive/Sheets/外部通信の権限承認を求められる。
`GEMINI_API_KEY: OK` と抽出済みフォルダ・書籍マスタの状況が表示される。

続けて `refreshBookMaster()` を実行し、「書籍マスタ」シートに刊行物が並ぶことを確認する。

### 6. ドライランで精度確認

`processFaxFolder()` / `extractOrders()` を手動実行 → シートを見て精度を確認する。
とくに**受注明細の冊数と書店コードは、実物のFAXと突き合わせて正答率を測ること**。
納得できたら `Config.js` の `DRY_RUN` / `ORDER.DRY_RUN` を `false` にして `npx clasp push`。

### 7. 自動運転ON

- `installTrigger()` → 1時間毎に `runPipeline()`（分類→抽出）が走る
- `installDailyReport()` → 毎日18時に日次サマリーメールが飛ぶ

両方を実行しておく。止めたいときは `removeTrigger()`（両方まとめて解除）。

## 関数一覧

| 関数 | 用途 |
| --- | --- |
| `setup()` | 初期化（ログシート作成・設定状況の確認） |
| `refreshBookMaster()` | openBD から自社刊行物を書籍マスタシートへ取り込む（新刊時に手動実行） |
| `runPipeline()` | 日常運転。分類 → 受注明細の抽出を続けて実行 |
| `processFaxFolder()` | ステージ1。分類して仕分け（DRY_RUN 尊重） |
| `extractOrders()` | ステージ2。受注FAXから明細を抽出（ORDER.DRY_RUN 尊重） |
| `dailyReport()` | 当日分を集計して日次サマリーをメール（動きがない日は送らない） |
| `installTrigger()` | 1時間毎のパイプライントリガーを設置 |
| `installDailyReport()` | 毎日18時の日次サマリートリガーを設置 |
| `removeTrigger()` | 関連トリガーをすべて解除 |

## テスト

GAS本体は動かせないが、純粋ロジック（ISBN検算・書名照合・要確認判定・
マスタ更新の upsert）は Node で検証できる。

```bash
npm test
```

`tests/` は `src/` の外に置いてある。`.clasp.json` が `skipSubdirectories: false`
なので、`src/` 配下に置くとテストまで GAS へ push されてしまうため。

## 注意

- DRY_RUN 中はファイルを移動しないため、同じPDFが毎回再処理されログが重複する。
  精度確認のための一時的な状態と割り切る（本番=移動ありにすれば解消）。
- `drive` スコープ（フルアクセス）を使う。Zapier が作ったファイルを移動するため
  `drive.file`（自作ファイルのみ）では不足するため。
- ISBNのチェックディジットは1文字の誤読を必ず検出するが、隣接桁の入れ替えは
  すり抜けることがある。そこは書籍マスタ照合で拾う。
